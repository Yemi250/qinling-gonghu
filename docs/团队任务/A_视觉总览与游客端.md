# A｜视觉总览与游客端

> 使用方法：本文件是可独立使用的完整任务提示词。将全文交给负责 A 的开发助手，并让其在团队仓库中工作。无需再拼接公共背景。
> 文档版本：2026-10-02。本文是实施任务说明，不代表相关功能已经完成。

## 产品背景与共同方向

我们正在参加西客松 AI 软件赛道，四人协作，约有三个完整开发日。旅游行业已确认可参赛。项目名为「秦岭共护」，定位为 **AI 驱动的景区生态共治平台**，核心主张是：

> 让每一次发现，都有一个回应。

秦岭提供地域背景与情感连接。我们希望从一个景区、一条步道开始，让游客提供线索，AI 整理信息，景区工作人员处置，管理者协调验收，游客获得反馈，呈现公众参与的生态保护愿景。

具体服务对象是景区运营企业的运营管理部门。企业痛点、合作关系和收益目前尚未通过真实客户验证；队友会尽量搜集照片和业务材料，演示中不得声称已有正式客户或真实治理成效。

### 本次优先级

1. 产品概念与故事表达：愿景有吸引力，价值一句话能讲清。
2. 前端视觉与交互：精致、有地域辨识度、手机和投影都清楚。
3. 参与和处置闭环：问题有人接、有人处理、有人回应。
4. 真实 AI 调用与基本运行稳定性：现场可操作，失败可恢复。

不以生产级识别准确率为本次目标，不训练模型、不做大规模精度评测、不建设复杂企业架构。功能范围收敛，呈现完整的小产品。上传、保存、调用、状态变化和反馈必须真实运行；样例材料明确标注“演示数据”，不能用预设答案冒充 AI。

### 唯一核心流程

游客上传照片、选择点位并填写描述 → AI 生成事件摘要与建议 → 信息不足时补充 → 管理员审核派单 → 工作人员提交整改照片 → AI 给出前后对比意见 → 管理员验收结案 → 游客查看结果与感谢卡。

主场景是一个示范景区内的垃圾散落、垃圾堆积或垃圾桶满溢。信息补充是条件分支，不是每次必经步骤。图像板块统一叫“AI 生态风险识别”，由 D 负责。

疑似烟雾、火点、水体异常可作为扩展类别，但必须复用同一套上报与人工复核流程；不另做灾害指挥系统，不自动触发真实应急联动。单张图片不能确定的地点、时间、污染性质和真实性，不写成确定事实。AI 辅助分析，管理员确认派单和结案。

### 视觉共同方向

- 总览：深墨绿、秦岭山形、等高线、克制的青绿点位动效。
- 业务页面：浅色背景、舒适留白、明确按钮、清楚的图片证据。
- 琥珀色表示待处理；红色仅用于必要提醒，不满屏告警。
- 最值得打磨的画面：总览首页、AI 事件卡、整改前后对比。
- 使用本地 SVG 示意地图；一个景区可实际操作，其他点位标注“规划展示”。
- 数字来自已保存记录，不编造“已接入景区”“今日投稿”数据。
- 动效围绕实际操作阶段展开，不假装执行未实现的真假检测、卫星核验等能力。
- 不加入商城、积分兑换、社区、排行榜、摄像头或无人机接入等支线。

## 团队分工与技术约定

| 人员 | 负责内容 | 工作分支 |
|---|---|---|
| A | 公共视觉、总览、游客端、反馈体验 | `feat/visitor-ui` |
| B | 管理工作台、派单、整改、验收 | `feat/admin-ui` |
| C | 后端、接口、存储、集成、运行交付 | `feat/backend` |
| D | 图像识别、AI 事件分析、整改对比、演示叙事 | `feat/ai-analysis` |

- 技术默认：React + TypeScript + Vite、FastAPI、SQLite、本地持久化图片目录。
- 一个仓库、一个后端；后端提供构建后的前端页面。密钥只通过服务端环境变量配置。
- 默认使用可配置的百炼 Qwen3-VL-Plus；D 首先验证账号实际可用性，如需替换，D 与 C 同步模型及输出契约。
- 不引入多 Agent 框架、微服务或复杂队列。依赖版本由 C 在工程初始化时锁定，所有人使用同一套依赖。
- 推荐模块归属：A 维护 `frontend/src/features/visitor/`、`overview/` 和公共视觉组件；B 维护 `frontend/src/features/admin/`；C 维护后端业务、API 与公共类型；D 维护 `backend/app/ai/`。C 初始化时确认实际目录，其他人不要另建互不兼容的工程。
- A 维护公共样式；C 维护接口与状态契约。涉及公共入口、依赖、类型或数据库的修改，先同步负责人。
- 前端早期允许使用约定样例并行开发，Day 1 晚上接通真实链路，最终演示使用真实调用。
- 每天中午和晚上集成一次；阻塞超过半小时立即同步。只修改自己负责的模块，避免覆盖他人工作。

## 共同接口与状态

以下是四人统一的最小接口约定，C 在开工首小时发布字段示例与错误返回；未经同步不得另起字段或路由。

统一用 `Event` 表示从线索到结案的记录，包含：编号、景区、点位、描述、原图、AI 分析、业务状态、责任人、整改图、复核说明、时间线。

| 方法与路径 | 行为 |
|---|---|
| `POST /api/uploads` | 上传原图或整改图，返回图片标识与展示地址 |
| `POST /api/events` | 保存事件，返回事件编号及游客查询凭证 |
| `GET /api/events` | 管理端事件列表与筛选 |
| `GET /api/events/{id}` | 事件详情；游客凭查询凭证访问自己的记录 |
| `POST /api/events/{id}/analysis` | 对已保存材料做线索分析或整改对比 |
| `POST /api/events/{id}/actions` | 补充、派单、提交整改、结案、退回、驳回 |
| `GET /api/overview` | 实际记录统计与示范点位 |

业务状态为“待补充、待审核、处理中、待验收、已结案、已驳回”。正常流程是待审核 → 处理中 → 待验收 → 已结案；缺失信息进入待补充，补齐后回到待审核；验收退回进入处理中；审核驳回进入已驳回。

AI 调用状态与业务状态分开。先保存材料再分析；超时或失败不丢失上报，可重试；重复分析不创建重复事件。管理员操作使用演示账号，游客查询凭证不能派单或结案。

D 提供两个模块接口，由 C 调用，不直接改工单：
- `analyze_report`：输入照片、点位、描述；输出可见现象、标题、摘要、类别、缺失信息、追问和处置建议。
- `review_resolution`：输入原图、整改图、处理说明；输出可见变化、无法确认事项和人工验收建议。

## 三天共同节奏与协作提交

| 时间 | 团队必须达到的结果 |
|---|---|
| Day 1 上午 | 统一视觉与接口，初始化工程，模型实际可调用 |
| Day 1 晚上 | 真实上传 → AI 分析 → 人工派单跑通 |
| Day 2 上午 | 整改 → 验收 → 游客反馈完整闭环 |
| Day 2 晚上 | 视觉打磨，第一次全流程彩排，形成缺陷清单 |
| Day 3 上午 | 修复阻断问题，完成手机与投影适配 |
| Day 3 下午至晚上 | 录视频、完成 PPT 与文档、彩排、冻结代码 |
| Day 4 9:30 前 | 核验并提交全部材料 |

Day 1 链路未通时暂停额外动画；Day 2 未闭环时砍掉辅助图表和规划点位效果，集中主流程。Day 3 24:00 冻结核心代码，之后只按赛规修复并注明明显运行时错误。

接受仓库协作者邀请后，克隆同一个仓库，从最新 `main` 创建自己的工作分支。逐步提交可运行成果，推送分支后发 PR，由队长统一合并。每天同步最新主分支，冲突与相关负责人一起处理，不强推覆盖他人提交。不提交密钥、`.env`、依赖目录或个人运行数据。

全组交付物包括：代码仓库、可运行 Demo、2—5 分钟演示视频、根目录项目说明、路演 PPT、API 使用清单；补充架构图、流程图和必要测试记录。不得把规划文档当成已实现能力。

最终验收关注：新图真实调用、主流程闭环、数据持久化、权限边界、失败可恢复、界面清楚好看。信息不足和无关图片不能被强行编成确定事件。不设准确率指标，不追求大规模测试。

## 你的身份与任务

你是 A，项目的视觉负责人，同时负责总览与游客端。请基于以上共同背景直接推进自己负责的实现，首要目标是让人第一眼理解秦岭生态共护，愿意提交线索，并在处理后获得明确回应。

### 必须交付

1. 公共视觉体系：颜色、字体层级、间距、按钮、卡片、状态标签与加载反馈；向 B 提供可复用组件。
2. 总览页：秦岭主题示意图、一个示范景区入口、实际事件统计、规划点位说明。
3. 游客上报：图片选择与预览、点位选择、描述输入、提交成功回执。
4. AI 事件卡：简洁呈现可见现象、摘要和建议；信息不足时可补充材料。
5. 游客进度：凭查询凭证查看时间线，结案后展示前后图片与感谢卡；回执提供可再次打开的查询入口。
6. 手机布局与大屏演示适配；准备供 PPT、录屏使用的统一视觉素材。

### 交互重点

- 总览负责气氛，表单负责易用；不要让复杂地图成为提交的前置条件。
- 展示“上传中、已保存、AI 分析中、待补充、待审核”等实际阶段。
- 模型等待时仍能查看已保存事件；失败给出明确说明和重试入口。
- 用户拒绝定位或未提供坐标时，仍能通过示范点位和文字描述完成上报。
- 空列表、无数据、上传失败、模型失败都有可理解反馈。
- 感谢卡表示线索获得回应，不凭空发放积分或生态贡献数值。

### 依赖与边界

你维护公共视觉，B 复用。C 提供上传、事件、详情和总览接口；D 的分析结果通过 C 接入。不要自行调用模型、计算另一套业务状态或另建后端。前端临时样例只用于开发，演示必须接真实接口。

### 个人排期

- Day 1 上午：定义视觉，交付公共组件和游客页面骨架。
- Day 1 下午：接通上传、创建事件、真实分析结果展示。
- Day 2 上午：补充信息、进度查询、结案反馈。
- Day 2 下午：总览、前后对比和关键动效，参加彩排。
- Day 3：修复视觉与交互问题，协助 PPT、视频，不再扩展支线功能。

### 完成判据与交接

手机能够完整上报并保留查询入口；B 完成结案后，游客重新查询能看到结果；总览数字和记录一致；页面在加载、无数据、失败和完成状态均可用。

提交 PR 时附关键页面截图、操作路径、已接接口、已知问题与验证结果，并标明公共组件变更。不要把仅有静态截图的页面标记为完成。
