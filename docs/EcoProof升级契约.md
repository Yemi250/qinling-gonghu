# EcoProof：证据、关联与整改核验

本轮在原有六景区、真实识图、派单与人工验收上增强三个能力。首页、景区画面、导航和收藏流程延续原有设计；不包含路线优化、积分、徽章或实际景区部署。

## 什么是证据分析

EcoProof 把一份投稿拆为四个可回读的阶段，而不是给照片编一个“真实性分数”。

| 阶段 | 实际工作 | 证据来源 |
|---|---|---|
| material 材料检查 | 文件已保存、图片可用、点位配置有效 | 系统检查；点位是游客选择 |
| content 内容分析 | 真实视觉模型提取可见问题、建议及缺失信息 | 模型分析 |
| association 关联线索比对 | 同点位近期候选检索、图片指纹与真实视觉比对 | 系统指纹及模型比对 |
| decision 处置建议 | 保存审核、补充、归并、无明显问题或人工复核建议 | 已完成阶段的材料 |

提交时间不是拍摄时间，游客选择的点位不是已验证的拍摄位置。SHA-256 相同证明规范化后的文件字节重复；dHash 接近只用于找候选，纯色图和不同图案都可能碰撞。任何指纹都不证明真实拍摄、同一事件、独立游客或违法行为。

任务在服务端后台执行，各阶段与结果存入 SQLite；刷新和关掉页面不会把已有阶段当成完成。运行中重复发起复用同一个任务。单 worker 重启会将中断任务标为失败，保留材料与已完成依据，提供重试入口。不同点位可并行；同点位的关联决策串行执行。该原型不是多进程任务队列，正常演示请使用 `--workers 1`。

## 什么条件允许归并

候选必须来自相同景区、点位和演示属性；目标是尚未结束的主事件（待审核或处理中），最近关联投稿的提交时间与新投稿相差不超过两小时。最多读取 50 个近期主事件、选择 3 个候选进行比对，不承诺全量事件检索。

完全重复图片只有同时满足以下条件才自动归并：新投稿尚未派单、状态待审核；双方的有效识图结果均为 `ok`；类别相同，且属于日常垃圾或水体外观类别；新投稿的全部原图 SHA-256 都已存在于目标组。疑似烟雾、火点与不确定类别不会自动归并。若真实模型对同图给出不同类别，保留人工确认，不为了演示放宽规则。

不同图片由真实视觉模型对照固定参照物、可见问题和不确定项，返回 `same_issue / different / uncertain`。相同垃圾类别并不足以证明同一事件。管理员先看依据和候选图片、选择候选，再点击确认；`different` 结果后端拒绝归并，`uncertain` 必须人工看材料。比对失败会明确标为部分完成，不会拿失败当成归并成功。

每份投稿保留原编号、图片、描述和游客凭证。归并只增加一层关系，管理员列表按主事件计数。`submission_count` 是投稿数，`unique_image_count` 是不同规范化图片数，`duplicate_image_count` 是图片数量减去不同图片数；这些字段均不是参与人数。处理在主事件上进行，其他投稿收到共同治理摘要。

误合并可由管理员填写原因后撤销。已结案或已驳回事件的关系不能撤销，已结案事件也不会因重复投稿自动重新打开。关系或材料变化会使旧候选、旧整改核验标为过期；请求使用版本号，过期点击返回 409，不覆盖新结果。

## 整改核验与人工结案

管理端从共同治理材料中选取最多 5 张不同整改前照片：优先主事件，再取近期关联投稿，明确显示完整数量与本次核验范围。模型只看到实际送入的图片，页面不宣称代表未送入材料。规范化图片完全重复的整改证据走 SHA-256 系统检查，记录模型名 `system:sha256`、`same_image=true`、`need_human`，不调用视觉模型，也不展示“建议通过”。

提供新整改照片后，真实模型输出可见变化、残留问题、不确定项及 `recommend_accept / recommend_reject / need_human`。建议通过不会自动结案。管理员仍须填写验收或退回说明；未运行模型、失败或旧结果过期时也可人工处理，但时间线明确记录人工验收，不假称 AI 通过。

游客只读取自己的原图、描述及受限分析记录；关联摘要只含主事件编号、点位、阶段、计数、里程碑和结案说明。管理员的候选照片、其他游客描述、其他投稿原图及完整整改核验材料清单不返回给游客。图片 URL 延续既有随机能力链接契约：知道链接可看图，本轮没有改为认证图片下载。

## 增量 API

原有上传、收藏、事件、动作和分析路径兼容。机器契约见 [OpenAPI](openapi.json)，前端类型由该快照生成。

| 路径 | 身份 | 结果 |
|---|---|---|
| `POST /api/events/{id}/proof` | 该投稿游客或管理员 | 202，创建或复用持久化任务 |
| `GET /api/events/{id}` | 该投稿游客或管理员 | 追加 proof、governance、revision、relationship_version、merged_into |
| `GET /api/events/{id}/associations` | 管理员 | 候选、过期标记、组内材料、整改前取样与完整数量 |
| `POST /api/events/{id}/merge` | 管理员 | 确认保存的当前候选，返回更新后的投稿 |
| `POST /api/events/{id}/unmerge` | 管理员 | 撤销尚未结束的关联，返回原投稿 |

归并请求：

```json
{
  "target_event_id": "32位目标事件ID",
  "source_revision": 1,
  "target_revision": 2,
  "reason": "管理员对照照片与关联依据后确认"
}
```

撤销请求：

```json
{"relationship_version": 2, "reason": "管理员复核发现为不同位置的问题"}
```

`proof.status` 为 `running / succeeded / partial / failed`；没有任务时 proof 为 null。阶段状态为 `idle / running / pass / attention / failed / skipped`，证据来源为 `system / visitor / model`。`proof.stale` 表示当前材料或关系已变化；失败保留已完成阶段，error 只返回可读的脱敏错误。

`GET /api/events` 仅列主事件；overview 的 total、by_status、closed_count、demo_count 与点位 event_count 按主事件统计。新增 submission_count 按全部投稿统计，today_count 延续按上海时区统计当天投稿数。界面用“治理事件”和“关联投稿”区分两种计数。

## 数据库与部署

数据库从 user_version=1 增量迁移到 2：上传增加 dHash 缓存；事件增加关系、关系版本和记录版本；新增 proof_runs 保存阶段、候选与建议。旧库首次升级前使用 SQLite backup API 备份到 `DATA_DIR/backups/before-v2-*.sqlite3`，迁移在事务中完成，不移动旧图片、不删除旧记录、不替换游客凭证。后续启动不会重复做同一版本迁移。新空库直接创建完整结构。

回退代码前应停服务并使用升级前备份配合对应版本，不能仅把旧代码指向已经升级的库。备份图片仍需保存完整 DATA_DIR。本轮未提供生产身份、多实例部署、分布式队列或灾害应急联动。

## 独立验收入口

```text
uv run pytest backend/tests backend/tests_ai -q
uv run ruff check backend scripts
npm --prefix frontend run build
npm --prefix frontend run test:e2e
uv run python -m scripts.live_upgrade_smoke
```

前四项离线或使用明确测试替身，不证明真实模型连接。最后一项需要服务端已配置的模型凭据，启动独立随机端口和系统临时数据库，并使用 [有标注的模拟图片](demo-fixtures/README.md) 请求真实模型。检查实际前后变化、保存、刷新、权限、人工结案、三个原凭证的共同回音及五个屏宽；同时验证同图整改负例没有调用模型。各次上游调用与失败尝试保留在隔离 evidence.json/ai_calls.jsonl，不记录密钥。

旧 `scripts.live_ai_smoke` 仍用于两张意境图的模型连接检查；其中同图整改现在只验证系统拒绝重复证据，不能再把该检查计为真实整改模型调用。
